3 Hosting & Performance

Revised 7 August 2026. The hosting questions this section raised in June are settled. The API no longer runs on Render, the cold-start problem is gone, and the stack is in production.

3.1 Where everything runs now

LayerWhere it runsState
Web clientVercel — global CDNRebuilds and publishes itself on every change. Awaiting the official domain (§4).
API serverAWS, ParisMoved off Render on 31 July after Render suspended the service. No cold starts. Answers in 0.4–1.1 seconds.

The June concern is resolved
Render's free plan slept after 15 minutes and made the next visitor wait up to a minute. That is gone: the API is always on, and a full release was measured putting 163 consecutive requests through a rolling deployment with none dropped — the site does not blink when it is updated.

3.2 Speed

Initial page weight fell from about 463 KB to 98 KB — 4.7× lighter. All 27 public pages were re-checked on 6 August: every one loads, with no broken images.

3.3 Credentials and configuration

Production settings are held in AWS Secrets Manager, not typed into a dashboard — the database string, the signing key, the media keys and the Institute's statistics key. Nothing sensitive sits in the code. The June list of environment variables no longer applies; two of the entries on it were never used by the software at all.

3.4 What it actually costs

Measured from the AWS bill on 7 August rather than estimated: the stack runs at about $2.27 per day — roughly $68 per month, plus MongoDB Atlas and the domain.

LineApprox. per month
Load balancer~$19
Network (NAT gateway, fixed IP address)~$34
API container~$11
Storage, monitoring, secrets~$4
Worth a decision — this is about double the June estimate
June put the figure at $33–37. The gap is not the API: the load balancer and container are almost exactly as forecast. It is the network charges — a NAT gateway and a fixed public address — which the estimate did not include. They are reducible with a configuration change that does not affect the site, and ADLM will bring a costed option. Flagged here rather than absorbed quietly, because a national institute should know what its infrastructure costs and why the first number moved.

4 Domain, DNS & SSL

Revised 7 August 2026. This is the one section still blocking launch.

4.1 What is already done

Canonical domain chosenniqs.org.ng — it is what the Institute's own email addresses use. niqsng.org should redirect to it rather than serve a duplicate site, which would otherwise split the Institute's search ranking between two addresses.
API access for the domainDone 6 August. The server now accepts requests from niqs.org.ng and niqsng.org. Until that change, every page would have loaded blank on the real domain.
SSL (https)Issued automatically once the domain is verified. Nothing to buy, nothing to renew.

4.2 What remains

The domain, the Institute's email, the member portal and the statistics API all run from a single cPanel account on the present host. Two records inside that account need to change — and one mail record needs protecting first. ADLM cannot begin until the cPanel login is provided (§15).

Why the order matters
The mail record for niqs.org.ng currently names the same address the website uses. Repoint the website first and mail to info@ and secretary@ — both printed on the site's own contact page — stops arriving. The fix is small and goes first: point mail at mail.niqs.org.ng, which already exists, wait, and test. Nameservers do not move, so the portal and the statistics API are untouched throughout.

4.3 At cut-over

The social-preview tags — the card shown when the site is shared on WhatsApp or LinkedIn — have since been repointed to niqs.org.ng, along with the redirects that collapse www., niqsng.org and the insecure http:// address onto the canonical one (§10.1). The holding page now covering the site retires itself automatically at launch.

6 Email / SMTP Activation Action needed

Revised 7 August 2026. Still the position reported in June: outgoing email is fully built and dormant, awaiting a mailbox. Nothing about it needs development.

Until it is switched on: event-registration confirmations do not send, members cannot receive their CPD “I attended” links, and admin password-reset links are written to the server log instead of being emailed. The contact form still records enquiries — they are simply read in the admin panel rather than arriving in an inbox.

The cPanel login in §15 closes this too
The Institute's mail already runs on that same cPanel account, so the sending mailbox can be created there in the same sitting — no new supplier, no extra cost, and the sender is already aligned with the domain, which is what keeps the mail out of spam folders. One credential closes both §4 and §6.

A dedicated mailbox rather than a person's account: it survives staff changes, and a personal password should never sit in a server configuration. ADLM loads these into AWS Secrets Manager and enables them — about ten minutes once the mailbox exists.

7 Payments Decision needed

The Payments and Membership pages currently display fee tables with a placeholder "payment coming soon" button. To go live with online payment, NIQS must choose one of:

OptionWhat it needs
A. Payment gateway on the website (Paystack / Flutterwave — Nigeria)A merchant account + API keys. Best if the website collects dues/exam/event fees directly.

Recommendation: if the membership portal will own dues/renewals, use Option B for member payments and reserve Option A only if the website needs to take standalone payments (e.g. public event tickets).

8 Membership Portal Integration

The member experience — login, the registered-QS directories, dues status, CPD, ID card — depends on the membership portal's API, which the portal team is building. This is fully specified in the companion document "Membership Portal — API Integration Requirements".

  • The website's portal client is already built and env-gated — it stays safely inert until the portal is ready, so it does not block a content launch.
  • When the portal team delivers, we simply set the PORTAL_* credentials and the member features come alive.
  • A content/marketing launch can go ahead now; the full member portal switches on once the API is available.

9 Security & Accounts (Pre-Launch Hardening)

  • Remove the test/seed endpoints. A setup endpoint currently lets anyone create a test member account (with credentials visible in the code). This must be removed and the test account deleted before launch. The one-time admin-seed endpoint should also be removed once real admins exist.
  • Set strong, unique secrets in production (JWT_SECRET, JWT_REFRESH_SECRET) — not the sample values.
  • Set NODE_ENV=production so login cookies are issued securely (HTTPS-only).
  • Create real admin accounts for Secretariat staff with the correct roles (national, state-chapter, WAQSN/YQSF sub-admins) and hand over credentials securely. Remove any test admins.
  • Verify sign-in works on the production domain (the website and API run on different addresses — confirm member/admin login and sessions behave correctly once the official domain is live).
  • Decide on the "Built by ADLM" credit badge shown on every page — keep as a credit, or remove for launch.
  • Optional hardening: rate-limiting on login and public forms; basic abuse protection on file uploads.

10 SEO, Analytics & Legal

Revised 11 August 2026. All five items this section listed in June are built and in the current release. What remains is two settings and one verification inside the Institute's own Google account, and three confirmations from the Secretariat on the legal wording.

10.1 What is already done

Web analytics Google Analytics 4, property NIQS Website, under an account registered in the Institute's own name. That last point is not a formality: Analytics cannot move data between properties, so a property created under the vendor's account would tie the Institute's traffic history to ADLM permanently. As set up, access can be handed over without losing a day of history.
Cookie notice Accept and Reject carry equal weight — a notice offering only "OK" is not consent under Nigerian law. Nothing is requested from Google until a visitor accepts: not the tracking code, not a preliminary ping. Decline or ignore it and no contact with Google is ever made.
Whose visits are counted The admin panel and the member area are excluded, so the figures describe the public rather than the Secretariat's own working day. Links that carry a private token — a flyer request, an event attendance link — are excluded too, since the address in those is itself the credential.
robots.txt and sitemap.xml Both returned not found on the live domain. The sitemap now lists 66 addresses including all 37 chapter pages, and is rebuilt automatically with every release so it cannot drift out of step with the site.
Social-preview tags Corrected to niqs.org.ng. They had been pointing at the temporary Vercel address, so every link shared on WhatsApp or LinkedIn was previewing an image from — and quietly advertising the address of — a staging deployment.
Favicon The small crest shown in a browser tab and beside a Google result. /favicon.ico was returning not found, and Google only displays an icon in search results when it is square and a multiple of 48 pixels, which the one linked was not. The full set has been regenerated from the crest.
One address, not four niqs.org.ng, www.niqs.org.ng, niqsng.org and the insecure http:// version all served identical pages. To a search engine that is four websites splitting between them whatever standing one would have earned. Three now redirect permanently to the fourth.
Privacy Policy & Terms of Use Published at /privacy-policy and /terms-of-use, linked from the footer of every page.
On the two legal documents
They are written against the Nigeria Data Protection Act 2023 and the NDPR, and against what this website actually does — every service provider named is one the software genuinely uses, and every category of information is one the system genuinely stores. A policy describing a generic website would be a published statement the Institute could not stand behind.
Three points are worth the Committee's attention. The membership portal is carved out — it is operated by another provider and holds the register itself, so the policy says so plainly and directs questions about membership records to the Secretariat. Storage outside Nigeria is disclosed: the database and application run in France and the hosting, image storage and analytics in the United States, which sections 41–43 of the Act require to be stated. And payments are described as not taken on this website, which is true today — that clause must be revisited before a gateway is connected (§7).

11 Backups & Monitoring

  • Enable automated database backups (a paid Atlas tier includes them) so member and content data is recoverable.
  • Set up uptime monitoring with alerts (e.g. UptimeRobot / Better Stack) so any outage is noticed immediately.
  • Optional: error tracking (e.g. Sentry) to catch issues proactively.

12 Pre-Launch QA Checklist

  • Test every form end-to-end: contact, event registration, flyer request, member sign-up / login / password reset.
  • Test admin create/edit/delete for each content type.
  • Check the site on mobile and across major browsers.
  • Check for broken links and that all images load from cloud storage (not the temporary local path).
  • Confirm email delivery once SMTP is set (§6), and the payment flow once the gateway is chosen (§7).
  • Run a performance/Lighthouse pass after the hosting upgrade.
  • After the first upload to the live domain (§10): confirm http://niqs.org.ng/about redirects to the secure canonical address rather than looping, and that /robots.txt, /sitemap.xml and /favicon.ico all load. A redirect rule that misfires takes the whole site down rather than degrading quietly, so this is checked on the spot, not the next morning.

13 Onboarding & Handover to NIQS

  • Admin training session — walk the Secretariat through managing content (news, events, leadership, chapters, journals, etc.) via the admin panel.
  • Secure credential handover — admin logins, plus access to hosting (Vercel, AWS), the database and media accounts as agreed.
  • Provide a short "how to update each section" guide alongside this document and the portal API document.
  • Agree ownership of ongoing content updates and a support / maintenance arrangement (point of contact, response times, update cadence).
